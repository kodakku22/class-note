# Release Signing & Auto-Update Setup

`electron-updater` **refuses to apply updates to unsigned installers** on
Windows and macOS. This is by design — without a code signature, an attacker
could swap the update binary mid-air. This guide walks through the one-time
setup needed before publishing the first signed release.

## Step 1: Obtain a Windows code-signing certificate

Three viable options for indie distribution:

| Provider | ~Cost (1 yr) | Notes |
|---|---|---|
| **SignPath.io OSS** | Free | For OSS projects. Sponsored signing on a managed signer. Best option for OSS. |
| **Sectigo OV (via SSL.com / GoGetSSL)** | $300–500 | Organisation Validated. Cheapest commercial. ~3–5 days SmartScreen warmup. |
| **DigiCert EV / Sectigo EV** | $400–700 | Extended Validation. Hardware token (USB / cloud HSM). No SmartScreen warmup. |

For ClassNotes (research workspace, OSS), **SignPath OSS** is the recommended starting point. Apply at <https://about.signpath.io/product/open-source>.

### Once issued

The signing provider gives you either:
- A `.pfx` file + password (Sectigo OV)
- A managed signing API (SignPath, DigiCert)

This guide assumes the `.pfx` + password case. For managed signing, follow the
provider's GitHub Action recipe instead.

## Step 2: Add GitHub Actions secrets

1. Encode the `.pfx` as base64:

   ```bash
   # macOS / Linux
   base64 -i classnotes-codesign.pfx | tr -d '\n' > cert.b64

   # Windows PowerShell
   [Convert]::ToBase64String([IO.File]::ReadAllBytes("classnotes-codesign.pfx")) | Set-Content cert.b64 -NoNewline
   ```

2. In your GitHub repository → Settings → Secrets and variables → Actions → New repository secret:

   | Name | Value |
   |---|---|
   | `WINDOWS_CERTIFICATE_BASE64` | contents of `cert.b64` |
   | `WINDOWS_CERTIFICATE_PASSWORD` | the password you set when exporting the .pfx |
   | `SENTRY_DSN` (optional) | your Sentry DSN, if using crash reporting |
   | `TELEMETRY_ENDPOINT` (optional) | your telemetry collector URL |

3. **Securely delete** `cert.b64` from your local machine. The `.pfx` itself should be stored in a password manager (1Password, Bitwarden) — **not** committed to the repo.

## Step 3: Set the publish target in `electron-builder.yml`

Once the GitHub repo is created and `package.json` has the real `repository.url`:

```yaml
# electron-builder.yml
publish:
  provider: github
  owner: YOUR-OWNER
  repo: YOUR-REPO
  releaseType: release
```

And update the release workflow's package step:

```yaml
# .github/workflows/release.yml
- name: Package Windows installers
  run: npx electron-builder --win nsis portable --publish always  # was: --publish never
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    ...
```

`GH_TOKEN` is auto-injected by GitHub Actions — no extra secret needed.

---

## Step 4: Tag and release

```bash
# Bump version in package.json
npm version patch  # or minor / major
git push --tags
```

The `release` workflow fires on `v*` tags, signs the binary, uploads to GitHub Releases as a draft, and generates SHA256 checksums.

Review the draft release, write the release notes, then publish. **The published `latest.yml` (auto-generated by electron-builder) is what auto-updater reads** — without it, in-app updates won't work.

---

## Step 5: Verify auto-update end-to-end

Critical: don't trust that signing works until you've actually verified an upgrade.

1. Install v0.1.0 on a test Windows machine
2. Publish v0.1.1 with a small visible change (e.g. new menu item)
3. Wait ≤ 1 hour (or open Settings → check for updates)
4. Confirm the app downloads, prompts, and applies the update without errors
5. Check `%USERPROFILE%\AppData\Roaming\ClassNotes\logs\main.log` — search for `update`

If you see `ERR_SIGNATURE_INVALID` or `Could not verify signature`, the signing chain is broken — usually wrong .pfx, wrong password, or missing intermediate CA cert.

## Useful commands

```bash
# Verify a signed binary locally
signtool verify /pa /v release/ClassNotes-0.1.0-Setup.exe

# Inspect electron-builder's publish manifest
cat release/latest.yml

# Compute SHA256 manually for comparison
certutil -hashfile release/ClassNotes-0.1.0-Setup.exe SHA256
```

## macOS / Linux

This document is Windows-only because that's the primary distribution target.
For macOS:
- Apple Developer ID + notarisation (`APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`)
- See [electron-builder mac signing docs](https://www.electron.build/code-signing-mac.html)

For Linux: AppImage signing is optional; `.deb` / `.rpm` packaging uses
separate keys. Out of scope for v1.
